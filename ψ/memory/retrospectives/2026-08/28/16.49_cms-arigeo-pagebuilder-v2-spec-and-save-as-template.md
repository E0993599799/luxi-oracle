had to be force-removed. None of this was task-difficulty — it was pure environment friction,
and I didn't have a fast way to detect "this operation is going to hang" before it happened.

## Lessons Learned

1. **Before writing any code in a checked-out repo you don't actively maintain, `git fetch` and
   diff local vs. remote first — a repo present on disk is not the same claim as a repo being
   current.** This applies everywhere, not just this session: any time you're about to implement
   against a local clone, treat staleness as a real, checkable hypothesis, not an edge case.

2. **When a target repo's working tree already has substantial unrelated uncommitted changes,
   never stage/commit broadly — `git add` only the exact paths you touched, and leave everything
   else exactly as found.** Someone else's (or an earlier session's) in-progress work is not yours
   to fold into your commit, even accidentally via `-A`.

3. **When a browser-automation tool starts timing out repeatedly on the same action (screenshot,
   scroll), switch strategy instead of retrying the same call — a text-extraction fallback that
   doesn't depend on rendering (like `get_page_text`) is often far more robust against
   virtualized/lazy-loaded or cross-origin content than pixel-based tools.**

4. **On a sandboxed Windows shell, prefer invoking a project's local binaries directly
   (`./node_modules/.bin/<tool>`) over `npx`/PATH-based resolution — PATH lookups inside a wrapped
   shell can fail silently or with a misleading "not recognized" error even when the binary is
   correctly installed.**
