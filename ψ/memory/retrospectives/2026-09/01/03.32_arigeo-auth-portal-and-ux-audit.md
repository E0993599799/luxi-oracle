## Lessons Learned

- When a user deprioritizes an in-progress bug diagnosis ("deploy first, fix later"), write the diagnosis to a durable file immediately — a chat-only diagnosis is lost the moment the session clears, and "later" often means a different session with no memory of it.
- When environment constraints block local verification (no network for `npm ci`, no build check), say so explicitly in the same message as the change summary, not just once early on — the user needs to know every subsequent push is unverified until they hear otherwise.
- If `/rrr` runs immediately after `/clear` with no work done in the new session, the retro must be reconstructed from the previous session's `.jsonl` plus `git log`/PR state, not skipped or faked from a template — the timeline is still recoverable, it just costs more tool calls than the normal "write from memory" path.
- Opening multiple small PRs for a sequence of visually-related tweaks is fine, but each one needs an explicit close-the-loop check (merged? still open? does the user know?) before considering the task done — don't let PR #20-style items go unmentioned in the final summary.
