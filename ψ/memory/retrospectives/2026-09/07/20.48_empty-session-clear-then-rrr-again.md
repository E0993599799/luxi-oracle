   specific to instruction-file bugs vs. code bugs, not something to generalize.

## Lessons Learned

- **When a session-metrics recurring-pattern note names a specific, applicable fix and
  the same friction shows up again later, apply the fix instead of writing another
  occurrence row.** The "3 occurrences → escalate" rule is a floor for *noticing*, not a
  ceiling on how many times the same diagnosed issue is allowed to recur before someone
  acts on the diagnosis.
- **Before trusting any shell one-liner in a skill's own documentation, run it against a
  real value and diff the result** — a documented command can itself carry the same class
  of bug the session is trying to avoid, especially path-encoding logic that only gets
  exercised on less-common inputs (space-containing paths, non-ASCII paths, etc.).
- **A thin `/clear`→`/rrr` session is still worth writing up honestly** if there's a
  genuine action to record (here: a cross-session root-cause fix) — the value isn't in
  session *length*, it's in whether something changed that future sessions benefit from.
