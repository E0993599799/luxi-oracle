# Size the memory artifact to what it tracks

When asked to "note something in memory," the reflex is to reach for the heaviest documented
mechanism — a full frontmatter'd `ψ/memory/learnings/*.md` file with `name`/`description`/`type`/
`ttl` and a "How to apply" section. That's the right weight for a durable, reusable pattern. It's
over-engineered for a one-off, self-expiring reminder like "check cloud routine X's run log next
time you're asked" — something that could just as well have lived as a `Next Steps` line in a
retrospective already being written in the same breath.

Caught 2026-09-03 (luxi-oracle): wrote a full memory file with a 7-day TTL for exactly this kind
of one-line reminder, when the retro I'd just finished writing already had a `Next Steps` section
that could have carried the same information with less apparatus.

## How to apply (generalizable, any project)

- Before creating a new frontmatter'd memory file, ask: is this a pattern worth surfacing to a
  *future, unrelated* session, or is it a reminder scoped to *this* specific thread of work? The
  former earns the full memory-file treatment; the latter usually doesn't.
- A retrospective's own `Next Steps` section is often sufficient for short-lived, self-obsoleting
  reminders — don't duplicate that into a separate memory file just because the skill instructions
  describe the memory-file path more thoroughly than the lighter alternative.
- Relatedly: before re-running a full default retro flow (background subagent + multi-section
  template) on a short tail segment, weigh whether a `--quick` or lighter mode would capture the
  same substance with less fixed overhead — size the *process*, not just the *artifact*, to the
  size of what happened.
